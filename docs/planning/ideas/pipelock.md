### Pipelock (https://github.com/pipelab-org/pipelock)
**Verdict:** Maybe — it already ships a Hermes plugin and is the one tool that would add content scanning (secret leaks, prompt injection) that Studio lacks, but only as an optional extra, not a core build.
**What it is:** An open-source "agent firewall" written in Go. It sits between an agent and the network: forward HTTP proxy, MCP proxy, per-tool hooks (Claude Code, Cursor, Hermes), and an OS sandbox. It scans traffic for leaked secrets (DLP), prompt injection, SSRF and tool poisoning, and writes signed "receipts" of each allow/block decision.
**Already in Studio/Hermes?** Partly. Studio has approvals (ask / guarded / auto, `approval-policy.ts`) that decide which actions need a human, and clean rooms (`docs/cleanroom.md`) with a host-allowlist proxy (`allowHosts`, `hostAllowed`). Hermes has its own write gate for memory and skills (`docs/hermes-write-gate.md`). All of these control WHO/WHERE (which host, which command). None of them look INSIDE traffic: a secret sent to an allowed host (e.g. a package registry or model API) or an injected instruction in a fetched page passes untouched. That content scan is the gap.
**How to use it in Hermes Studio:**
1. Install the pipelock binary (or the `ghcr.io/pipelab-org/pipelock` Docker image) next to Studio / in the Hermes runtime.
2. Run `pipelock hermes install --mode full --pipelock-config <file>`: it installs a Hermes Python plugin (pre_tool_call, transform_tool_result hooks) and edits `~/.hermes/config.yaml` (backs it up first). `pipelock hermes verify` checks it. Use the `balanced` or `strict` preset, start in audit mode.
3. Optional: `--mode mcp-only` just wraps MCP servers.
4. Clean rooms: run pipelock as the upstream of the existing allowlist proxy (or replace it), so room traffic is also content-scanned.
**How to use it in herdr:** Not directly relevant; herdr is a terminal multiplexer and has no network layer. Agents in herdr panes are covered only if they run in a clean room or have `HTTPS_PROXY` pointed at pipelock (or are started via `pipelock sandbox -- <agent>`).
**How to integrate it properly (build work):**
- Small: docs page + a Settings toggle that runs the install command and shows `verify` output (Hermes settings page).
- Small/medium: add a "pipelock" network mode to `services/cleanroom/index.ts` (chain the allowlist proxy to a pipelock container, env `HTTPS_PROXY`; clean-room agents are no-internet so the proxy is a hard boundary, which is where pipelock is strongest).
- Medium: read pipelock's audit log / receipts and show blocks in the Studio approvals or Inbox (and as a herdr Inbox item). Needs a log tail and a small UI list.
- Not worth building: our own copy of its scanners.
**Risks:** Hermes plugin changes the user's `config.yaml` and relies on Hermes' plugin API (version drift; they test against a pinned Hermes). Terminal coverage is "cooperative" (agent must honour proxy env) unless sandboxed. TLS interception (needed to see inside HTTPS) means trusting a local CA; off by default. False positives will block agents (tune with audit mode). Licence is split: core Apache-2.0, `enterprise/` dir is Elastic License 2.0 (multi-agent profiles, license service); stay on the core. Pre-built release binaries/images may include paid-tier features; the repo Dockerfile builds Community-only. Very active project with large changelog, so upgrade churn is high. Another process to run on the NUCs/Unraid (small Go binary, light).
**Facts:** Apache-2.0 core + ELv2 enterprise dir; last commit 2026-11-20 (cloned today); latest release v3.8.0 (3.8 line, Unreleased section in changelog); Go 1.26; ~8.5k files, CNCF landscape listed, OpenSSF scorecard; star count not visible from the clone.
