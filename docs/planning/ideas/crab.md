### CRAB — Clean Rebuild of Anything's Behavior (https://github.com/lemonadesaltbagel/crab)
**Verdict:** Skip as a feature, but borrow ideas — it is a legal "clean-room reimplementation" tool, not an agent sandbox like Studio's; a few of its container-hardening and audit ideas are worth copying.
**What it is:** A Python tool (MCP server + CLI) that lets one agent (the "observer") study an app as a black box (CLI, web via Playwright, Android) and write a sanitized behavior spec. A gate checks the spec for copied text/real names, then a second agent (the "clean implementer") rebuilds the feature from only that spec and gets abstract pass/fail back. Both agents can run in enforced Docker rooms (internal network + allowlist egress proxy). The name "clean room" means legal separation of knowledge, not just a sandbox.
**Already in Studio/Hermes?** Only the container part overlaps. Studio's clean room (`docs/cleanroom.md`, `services/cleanroom/index.ts`) already has per-chat container, `--network none`, allowlist proxy over Unix sockets, model proxies, no-new-privileges, dropped caps, cpu/mem/pids limits, herdr pane integration, per-room home. Nothing in Studio does behavior observation, spec gating or clone verification.
**How to use it in Hermes Studio:** Not needed day to day. If the user ever wants "rebuild feature X from an app without seeing its code", run `crab observe --port` on the host and add it as an MCP server in a coding-agent chat; use `uv tool install` (not in Studio's image). Otherwise leave it out.
**How to use it in herdr:** Not relevant — herdr is a terminal multiplexer; CRAB has no UI or pane hooks.
**Ideas worth borrowing for Studio's clean rooms (build work):**
- Egress log (small): CRAB's proxy writes every allowed/refused attempt as a JSON line (`egress.jsonl`). Studio's `handleProxy` could log the same per room and show "blocked hosts" in the chat header, so the user can add to `allowHosts` in one click.
- Isolation self-check (small/medium): `crab cleanroom check` runs probes from inside the container (no direct internet, proxy refuses example.com, project dir not visible, only expected mounts). Add a "Test clean room" button/endpoint that runs the same probes with `docker exec` and shows pass/fail.
- Read-only root + tmpfs (small): CRAB runs `read_only: true`, `cap_drop: ALL`, non-root user, tmpfs `/tmp`. Studio drops only 4 caps and runs as root with a writable root fs; try `--read-only --tmpfs /tmp --cap-drop ALL` and a non-root user as an option (watch that agents/installs still work; mount `/root` home is already writable).
- Exact `host:port` allowlist (small): CRAB matches host AND port; check Studio's allowlist does the same (no wildcard widening).
- Managed settings for the agent (small): CRAB ships `/etc/claude-code/managed-settings.json` that denies WebSearch/WebFetch and turns telemetry off inside the room. Studio could write the same file into Claude Code clean rooms.
- Hash-chained audit log (medium, optional): append-only, hash-linked JSON lines of room events (started, host allowed/denied, approval). Cheap tamper evidence for Agent work approvals; skip DSSE signing.
- Two-room pattern (large, only if wanted): an "observer room" that can only reach a target through one MCP tool, and a "reader" room with no network. Fits a future "research then build" flow, not needed now.
**Risks:** Early software (0.4, one commit visible in the shallow clone), single maintainer, tiny community; legal risk is on the user (reimplementing products). Needs Docker host access, Playwright Chromium, Android SDK for some targets. Its rooms share the host kernel (its own docs say so) and the model API is open by design. Nothing found that phones home; I did not run it.
**Facts:** Apache-2.0; last commit 2026-11-03 (v0.4.0, 2026-11-02, renamed from Teardown); Python 3.12+, on PyPI as `crab-cleanroom`; stars not checked (GitHub API not available here). Files read: README, docs/clean-runtime.md, deploy/cleanroom.yaml, gate/egress.py, audit/log.py.
